日期：2026-09-21～23。范围：M1 的 T-06～T-11 及其后的答疑与理解检查。
实现证据以 `specs/education-service-agent/progress.md` 为准，本文只记录学习过程。

## 1. T-06：数据库约束

**Q1（已通过）**：部分唯一索引为什么比"先查后插"可靠？两个请求同时到达会怎样？
- 学员初答：能防止业务层 bug 造成不一致。
- 补充讲清楚的机制：先查后插存在 SELECT 到 INSERT 之间的时间窗口，两个并发请求都能在对方提交前读到"未结束申请数=0"，都判定可以插入，最终各自成功、破坏不变量（check-then-act 竞态，TOCTOU）。唯一索引把判断下沉到 INSERT 时刻本身，不存在这个窗口——这是"用设计定义掉特殊情况"的具体例子。

**Q2（已通过，学员初次未答出）**：金额已经有 `CHECK (refunded_cents <= paid_cents)`，为什么 M2 的退款事务还要锁订单并重新校验？
- 关键点：CHECK 只保证"提交时这一行的最终数值关系成立"，不保证"这次操作基于的是最新值"。两个并发退款请求若都基于同一份旧 `refunded_cents` 读数计算新值，后提交的会覆盖先提交的结果（lost update），且覆盖后的值仍可能满足 CHECK——CHECK 管不住"基于哪个版本的数据计算"，只有显式锁（`SELECT ... FOR UPDATE`）+ 重新读取校验才能堵住。

## 2. T-08：认证 vs 授权

讲在动手写代码之前：认证回答"你是谁"（登录换 session），授权回答"你能做什么"（已知身份后，对具体资源有没有权限）。前端隐藏按钮不是授权，请求照样能直接打到后端；授权必须在服务端、针对每个具体资源做。

学员独立手写 `GET /me/enrollments/:id/progress` 的授权判断（先给失败测试 + 骨架 + TODO 注释，不给答案），经过几轮 review：
1. 条件取反（`if (enrollment)` 应为 `if (!enrollment)`）——把整个授权判断的方向写反了，是最要命的一处。
2. SQL 语法错误（`SELECT id,  FROM` 多余逗号）。
3. 查错表/字段（`learning_progress` 写成 `lessons`，取 `v.id` 应为 `v.lesson_id`）。
4. 缺 `student_id` 过滤——反向验证证明：去掉这行过滤，4 个测试**照样全绿**，因为测试夹具里每个学员用的是独立班期、没有共享课次。教训：**测试全绿只能证明"写了的用例"过了，证明不了"没想到的场景"也安全**。
5. 箭头函数返回对象字面量少括号（`v => {lessonId: ...}` 会被解析成代码块，恒返回 `undefined`）。
6. `any` 换成精确类型：讨论了"要不要每个查询都定义具名 interface"——判断标准是"这个形状会不会在第二个地方复用"，只用一次的查询结果用内联类型字面量就够，具名 interface 留给像 `SessionUser` 那样真正跨多处复用的领域概念。过程中发现一处类型标注本身是假的（`status: boolean`，实际是三态字符串枚举），提醒：类型标注只能防"手滑写错字段名"，防不了"标的类型本身就是错的"，pg 驱动返回值是 `any`，TS 不会替你去核对数据库实际类型。

## 3. T-09：公开数据 vs 私有数据

**Q1（已通过）**：`/catalog/current` 为什么能公开、`/me/enrollments` 必须登录？
- 学员答：公开信息（课程标题、价格、开课时间）是"谁都可以看的，学员看了才能决定要不要报"；`/me/enrollments` 返回的是具体某个学员的私有数据，必须确权。

**Q2（已通过）**：`publicFacts`/`rights` 两个字段固定返回空数组、不拼假数据，如果换成"先拼一份看起来合理的假数据"会有什么后果？
- 学员答：可能误导调用方。
- 补充：不只是"可能"，是必然——调用方（前端页面、以后接进来的模型）没有办法分辨"这是真数据"还是"临时占位数据"，只会把返回内容当权威事实直接使用。如果 `publicFacts` 塞了编出来的营销文案，最后可能变成模型信誓旦旦地告诉学员一个不存在的课程卖点——这是 AC-001"不编造业务事实"在 API 层的具体体现。

## 4. T-10：并发与锁

**Q1（已通过）**：`progress/import` 一条不合法就整批 422，对老师批量导入的影响？
- 学员答：会影响数据合理的学员的导入——不方便。

**Q2（已通过，分两轮讲清楚）**：`cohorts`/`lessons` 的更新端点为什么不像 `applications` 那样带乐观锁（`expectedRevision`）？
- 学员初答两点，都准确：①`applications` 涉及学员和老师双方竞态，`cohorts` 只有老师单方操作，安全一些；②后果轻重不同，`applications` 状态错了对双方都麻烦，`cohorts` 影响小。
- 追问"什么场景会让这个决定不再成立"：学员这两点其实是"当前为什么成立"的准确理由，但往前推一步——"老师单方操作不涉及竞态"这个前提，成立的条件是"同一个班期只有一个老师在管"。当前 `requireRole("teacher")` 只校验角色，没有校验"你是不是这个班期的老师"，任何老师都能改任何班期。如果两个老师同带一门课，或者批量导入脚本和人工编辑同时跑，竞态就从"学员 vs 老师"变成"老师 vs 老师（或程序）"。
- 学员最后自己总结到位：加锁是为了解决竞态问题，我们没引入不是这类资源天生不需要锁，是当前状态还不需要考虑——**决定的正确性绑定在"当前没有多方并发编辑同一资源"这个假设上，假设变了要跟着重新评估，不是先加上以防万一**。

## 5. M1 门槛讲解：course/version/cohort、认证/授权分层

### course / version / cohort
三层从抽象到具体：Course（长期产品，不可报名）→ Course Version（内容快照，新版本新增一行不覆盖旧版本）→ Cohort（某版本的一次具体开课，学员报的是这个）。
核心原因：**"我买的是什么"必须能精确回答，且答案不随时间变化**。报名绑定具体班期、班期绑定具体版本，版本内容不会被后续更新覆盖——这是 `/me/enrollments/:id/schedule` 能稳定返回课表的前提。

**Q（已通过）**：不拆版本会出什么问题？
- 学员答：学员买的是一次具体版本的课程，每个版本内容不一样，买了哪个就只能看哪个；不拆版本就没办法回答清楚课程更新以后他能看到的东西。

### 认证 vs 授权的两层
认证：你是谁（登录）。授权在这个项目里拆成两层，容易被合并理解但其实是两件独立的事：
1. **角色授权**（`requireRole("teacher")`）：粗粒度，只看角色标签。
2. **资源授权**（`WHERE student_id = $1`）：细粒度，必须落到具体的行。

角色授权挡得住"学员访问老师接口"，挡不住"学员 A 访问学员 B 的报名"——两人角色一样，问题在具体资源归属。前端 `RequireAuth` 只做第 1 层，第 2 层的判断权在后端，前端拿不到也不该拿到"这条数据是不是他的"这个真相。

**Q（已通过）**：学员 A 想看学员 B 的报名，角色授权和资源授权分别会不会拦住他？
- 学员答：角色授权是学生角色，理论上可以看报名，这一层拦不住；资源授权上没有 B 的权限，需要在这一层拦他。
