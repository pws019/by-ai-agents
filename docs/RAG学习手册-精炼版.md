# RAG 学习手册：从初体验到工程落地

目标：用最短路径理解 RAG，并能完成一次可用的知识库问答初体验。重点包括：RAG 核心概念、可视化 RAG、向量数据库选择、Cherry Studio / IMA 初体验、分块策略、评估与工程步骤。

---

## 1. RAG 是什么

RAG = Retrieval-Augmented Generation，检索增强生成。

一句话：

```text
RAG 不是让模型学会新知识，而是在回答前先帮模型查资料。
```

基本流程：

```text
用户问题
-> 检索知识库
-> 找到相关文档片段
-> 把片段塞进 prompt
-> 大模型基于片段回答
```

RAG 解决的是：

```text
模型不知道你的私有资料
模型知识过期
模型容易编造
公司文档太多无法手动查
回答必须引用资料来源
```

RAG 不适合解决：

```text
让模型固定语气
让模型稳定输出 JSON
让模型学会你的分类标准
让模型执行复杂工作流
```

这些更适合 Prompt / LoRA / 工具调用。

---

## 2. RAG 和微调的区别

最核心区别：

```text
LoRA / 微调: 改模型怎么做
RAG: 给模型查什么资料
```

| 场景 | 推荐 |
|---|---|
| 售后政策、产品手册、FAQ 问答 | RAG |
| 固定客服语气、固定 JSON、意图识别 | LoRA / QLoRA |
| 查询订单、库存、物流、退款状态 | API / 工具 |
| 设定身份、回答边界、输出要求 | Prompt |

客服机器人最佳组合：

```text
Prompt: 规则边界
LoRA: 客服行为模式
RAG: 产品和政策知识
API: 实时业务状态
```

---

## 3. RAG 的最小闭环

一个最小 RAG 系统只需要 5 件事：

```text
1. 文档
2. 分块
3. 向量化
4. 检索
5. 生成回答
```

对应技术：

| 环节 | 作用 |
|---|---|
| 文档解析 | 读取 PDF、Word、Markdown、网页 |
| 分块 Chunking | 把长文档拆成可检索的小片段 |
| Embedding | 把文本变成向量 |
| 向量数据库 | 存储向量并做相似度搜索 |
| Rerank | 对召回结果二次排序 |
| LLM | 基于检索结果生成回答 |

---

## 4. 可视化 RAG 怎么理解

可视化 RAG 不是一个单独技术，而是把 RAG 流程显示出来，方便调试。

你应该能看到：

```text
用户问题是什么
检索到了哪些 chunk
每个 chunk 的相似度分数
是否经过 rerank
最终给模型的上下文是什么
模型引用了哪些来源
回答是否基于资料
```

可视化 RAG 的价值：

```text
发现为什么答错
发现是不是没检索到正确资料
发现 chunk 是否切坏了
发现 top_k 是否太小
发现 embedding 模型是否不适合中文
发现文档解析是否丢内容
```

调试 RAG 时优先看：

```text
问题 -> 检索结果 -> 最终上下文 -> 回答
```

如果检索结果错了，别急着换大模型，先修分块、embedding、向量库、rerank。

## 5. RAG 分块策略

分块是 RAG 的核心。分块不好，后面模型再强也容易答错。

### 5.1 固定大小分块

把文档按固定长度切，比如 500 tokens。

```text
优点: 简单，成本低，适合 Demo
缺点: 可能切断语义，上下文不完整
```

建议参数：

```text
chunk_size: 300-800 tokens
chunk_overlap: 50-150 tokens
```

适合：

```text
快速原型
FAQ
短文档
结构不复杂的说明文
```

### 5.2 语义分块

按照段落、主题句、语义边界切分。

```text
优点: 语义完整性更好
缺点: 实现复杂度更高
```

适合：

```text
政策文档
法律条款
医疗说明
技术手册
长文章
```

### 5.3 递归分块

先按大结构切，再逐级拆成小块。

常见顺序：

```text
章节
-> 小节
-> 段落
-> 句子
-> 固定长度
```

```text
优点: 兼顾上下文完整性和检索粒度
缺点: 需要额外分层逻辑
```

工程里最常用：

```text
文档结构分块 + 递归分块
```

### 5.4 基于文档结构的分块

利用 Markdown 标题、PDF 标题、表格、列表、章节来切分。

```text
优点: 充分利用文档格式信息
缺点: 对纯文本或解析差的 PDF 效果一般
```

适合：

```text
Markdown 文档
产品手册
API 文档
规章制度
带目录的 PDF
```

### 5.5 基于 LLM 的分块

让大模型判断怎么切最合理。

```text
优点: 智能，适合复杂文档
缺点: 成本高，速度慢，不适合大规模实时处理
```

适合：

```text
高精度问答
法律 / 医疗 / 金融资料
复杂长文档
重要知识库离线处理
```

### 5.6 分块选择建议

| 场景 | 推荐策略 |
|---|---|
| 快速 Demo | 固定大小分块 |
| 工程文档库 | 文档结构分块 + 递归分块 |
| 法律 / 医疗高精度问答 | 语义分块 + LLM 辅助分块 |
| FAQ | 一问一答为一个 chunk |
| 表格多的文档 | 表格单独抽取，不要硬切 |
| Markdown / API 文档 | 按标题层级切 |

第一版建议：

```text
chunk_size: 500 tokens
chunk_overlap: 100 tokens
top_k: 5
rerank_top_n: 3
```

## 6. Embedding 模型选择

Embedding 负责把文本变成向量。

选型原则：

```text
中文资料 -> 选中文或多语言 embedding
英文资料 -> 英文 embedding 可选更多
中英混合 -> 多语言 embedding
本地私有化 -> 本地 embedding
追求简单 -> 云端 embedding API
```

常见选择：

| 类型 | 适合 |
|---|---|
| 云端 embedding | 快速原型、免部署 |
| 本地 embedding | 私有文档、安全要求高 |
| 多语言 embedding | 中英混合知识库 |
| 领域 embedding | 法律、医疗、代码等专业知识库 |

第一版不要过度纠结，先保证：

```text
文档能解析
chunk 能检索到正确内容
回答能引用来源
```

## 7. 向量数据库怎么选

向量数据库负责存储 embedding，并根据问题向量找相似文档片段。

### 7.1 选择表

| 工具 | 适合场景 | 特点 |
|---|---|---|
| Chroma | 本地 Demo、个人项目 | 简单，启动快 |
| FAISS | 本地高性能检索 | 轻量，适合本地实验 |
| Milvus | 大规模向量检索 | 工程能力强，适合服务端 |
| Qdrant | 中小型生产、过滤条件多 | API 友好，部署相对简单 |
| Weaviate | 语义搜索平台化 | 功能丰富 |
| pgvector | 已经用 PostgreSQL | 架构简单，适合业务系统集成 |
| Elasticsearch / OpenSearch | 关键词 + 向量混合检索 | 适合已有搜索体系 |

### 7.2 最直接建议

```text
个人学习 / Demo:
Chroma 或 FAISS

业务系统已经有 PostgreSQL:
pgvector

想认真做生产服务:
Qdrant 或 Milvus

需要关键词 + 向量混合搜索:
Elasticsearch / OpenSearch
```

### 7.3 不要一开始就重型化

第一版不要上来就纠结 Milvus 集群。

正确顺序：

```text
先用 Chroma / FAISS 跑通
确认分块和检索有效
再根据数据量和并发迁移 Qdrant / Milvus / pgvector
```

## 8. 检索策略

### 8.1 向量检索

根据语义相似度找 chunk。

适合：

```text
用户说法和文档说法不完全一样
同义表达
自然语言问答
```

### 8.2 关键词检索

根据关键词、编号、术语精确匹配。

适合：

```text
订单规则编号
法律条款编号
产品型号
错误码
API 名称
专有名词
```

### 8.3 混合检索

同时用向量检索和关键词检索。

推荐：

```text
Hybrid Search = Vector Search + Keyword Search
```

适合真实业务：

```text
用户自然语言问题
+ 文档里有很多专有名词、编号、型号、条款
```

### 8.4 Rerank

Rerank 是对初步召回的结果再次排序。

流程：

```text
先召回 top_k = 10-20
再 rerank 选 top_n = 3-5
最后给 LLM
```

Rerank 的价值：

```text
提升相关性
减少错误 chunk 进入 prompt
降低大模型被无关资料误导
```

## 9. Cherry Studio 初体验

Cherry Studio 适合做本地大模型和知识库体验。

建议初体验目标：

```text
能添加模型
能创建知识库
能上传文档
能问答
能看到引用来源
能对比分块效果
```

推荐步骤：

```text
1. 安装 Cherry Studio
2. 配置一个大模型
   可以是云端 API，也可以是本地 Ollama 模型

3. 配置 embedding 模型
   中文文档优先选中文或多语言 embedding

4. 新建知识库
   上传 PDF / Markdown / txt

5. 设置分块参数
   chunk_size 先用 500
   overlap 先用 100

6. 开始提问
   先问文档中明确存在的问题

7. 检查引用
   看回答是否真的来自检索片段

8. 调参数
   答不准先调分块、top_k、embedding，不要先怪大模型
```

适合测试的问题：

```text
文档里某个定义是什么？
某个流程分几步？
某个规则的例外条件是什么？
请根据文档总结某一章。
请列出文档中提到的限制条件。
```

不适合一开始测试：

```text
跨 10 个文档综合推理
需要实时数据的问题
文档里根本没有答案的问题
```

## 10. IMA 初体验

IMA 可以用来做资料收集、文档阅读和知识管理初体验。

建议把它当作：

```text
个人知识库入口
文档问答工具
资料整理工具
RAG 思维训练工具
```

初体验路线：

```text
1. 准备 3-5 个同一主题文档
   例如售后政策、产品手册、FAQ、内部流程

2. 导入 IMA
   先做一个小知识库，不要一次导入太多

3. 提问事实型问题
   例如：退货条件是什么？

4. 提问总结型问题
   例如：帮我总结售后流程。

5. 提问对比型问题
   例如：退款和换货流程有什么不同？

6. 检查引用和来源
   看答案是否能回到原文。

7. 记录错误
   是没检索到，还是检索到了但总结错了。
```

使用 IMA 的重点不是“它回答得像不像人”，而是训练你观察：

```text
知识库是否覆盖问题
文档是否结构清晰
问题是否能命中正确资料
回答是否有来源依据
```

## 11. 一个标准 RAG 工程架构

```text
文档源
  -> 文档解析
  -> 清洗
  -> 分块
  -> embedding
  -> 向量数据库
  -> 检索
  -> rerank
  -> prompt 拼接
  -> LLM 生成
  -> 引用来源
  -> 日志与评估
```

服务结构：

```text
前端
  -> 后端 API
  -> RAG 检索服务
  -> 向量数据库
  -> 大模型服务
  -> 返回答案 + 引用
```

## 12. RAG 的关键参数

第一版推荐：

```yaml
chunk_size: 500
chunk_overlap: 100
top_k: 5
rerank: true
rerank_top_n: 3
temperature: 0.2
answer_with_citation: true
```

参数解释：

| 参数 | 作用 | 建议 |
|---|---|---|
| `chunk_size` | 每块多长 | 300-800 tokens |
| `chunk_overlap` | 相邻块重叠 | 50-150 tokens |
| `top_k` | 召回多少块 | 5-10 起步 |
| `rerank_top_n` | 最终给模型几块 | 3-5 |
| `temperature` | 回答随机性 | 知识库问答用 0-0.3 |
| `score_threshold` | 相似度阈值 | 低分不要强答 |

## 13. RAG Prompt 模板

建议强约束模型只基于资料回答。

```text
你是一个严谨的知识库问答助手。

请只根据【参考资料】回答用户问题。
如果参考资料中没有答案，请回答“根据当前资料无法确认”，不要编造。
回答要简洁、准确。
如果能定位来源，请列出引用片段编号。

【参考资料】
{context}

【用户问题】
{question}
```

客服版：

```text
你是客服知识库助手。

请根据【公司资料】回答用户问题。
如果资料中没有明确说明，不要承诺退款、赔偿、时效或价格。
遇到订单、物流、库存、退款状态，请提示用户提供订单号并通过系统查询。

【公司资料】
{context}

【用户问题】
{question}
```

## 14. RAG 评估怎么做

不要只看“回答像不像”。

要看：

```text
检索是否命中正确 chunk
回答是否忠于资料
是否引用来源
不知道时是否拒答
是否把多个文档混错
是否遗漏关键限制条件
```

最小评测集：

```text
20 个事实型问题
10 个总结型问题
10 个边界/例外问题
10 个资料中没有答案的问题
```

核心指标：

| 指标 | 含义 |
|---|---|
| Recall@K | top_k 里有没有正确资料 |
| Answer Accuracy | 回答是否正确 |
| Faithfulness | 是否忠于检索资料 |
| Citation Accuracy | 引用是否对应原文 |
| Refusal Accuracy | 没资料时是否不编造 |

## 15. 常见问题与处理

### 15.1 回答胡说

优先检查：

```text
检索结果是否正确
prompt 是否要求只能基于资料
temperature 是否太高
是否没有设置低分拒答
```

### 15.2 检索不到正确内容

优先检查：

```text
分块是否切坏
chunk 是否太大或太小
embedding 是否适合中文
top_k 是否太小
是否需要关键词检索
是否需要 rerank
```

### 15.3 答案漏掉限制条件

处理：

```text
增大 top_k
启用 rerank
优化 chunk overlap
按章节结构分块
让 prompt 要求列出例外和限制
```

### 15.4 PDF 表格内容丢失

处理：

```text
换 PDF 解析工具
表格单独抽取成 Markdown / CSV
不要把表格硬切成普通文本
```

### 15.5 多文档冲突

处理：

```text
记录文档版本
加入更新时间 metadata
检索时优先最新版本
回答中说明来源
```

## 16. 学习路线

### 第 1 阶段：工具初体验

```text
Cherry Studio:

IMA:
导入资料 -> 问事实问题 -> 问总结问题 -> 检查来源
```

目标：


重点掌握：

```text
chunk_size
chunk_overlap
embedding
top_k
rerank
向量数据库
引用来源

```


加入：


## 18. 最终建议

第一版不要复杂。

```text
工具:
Cherry Studio / IMA 做初体验

分块:
固定大小 500 tokens + overlap 100 起步

向量库:
Chroma / FAISS 起步

检索:
top_k = 5
有条件加 rerank

回答:
必须基于资料
必须能引用来源
资料没有就拒答
```

真正进入工程后：

```text
文档结构分块 + 递归分块
混合检索
rerank
metadata 过滤
引用来源
评测集
日志观测
权限控制
```

一句话结论：

```text
RAG 的核心不是“大模型多强”，而是文档解析、分块、检索和引用是否可靠。
```
