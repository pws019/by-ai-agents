### T-06 理解检查题（已完成）
- Q1（部分唯一索引 vs 先查后插）：学员答"能防止业务层 bug 造成不一致"，补充具体机制：先查后插存在 SELECT 到 INSERT 之间的时间窗口，两个并发请求都能在对方提交前读到"未结束申请数=0"，都判定可以插入，最终各自成功、破坏"至多一条未结束申请"的不变量（check-then-act 竞态）。唯一索引把判断下沉到 INSERT 时刻本身，不存在这个窗口。
- Q2（CHECK 为什么不够，退款还要锁订单重新校验）：学员未答出，已讲解：CHECK 只保证"提交时这一行的最终数值关系成立"，不保证"这次操作基于的是最新值"。两个并发退款请求若都基于同一份旧 `refunded_cents` 读数计算新值，后提交的会覆盖先提交的结果（lost update），且覆盖后的值仍可能满足 `refunded_cents<=paid_cents`，CHECK 全程不会报错——它管不住"基于哪个版本的数据计算"这件事，只有显式锁（`SELECT ... FOR UPDATE`）+ 重新读取校验才能堵住。

| seed 数据 id 固定为 `00000000-0000-0000-0000-0000000000xx`，姓名/课程名带"（合成数据）"后缀，`orders.source='seed'` | 多重标记确保"数据明确标记合成"：id 本身、可读文本、数据库字段三处都能识别，不依赖单一约定 |
| seed 用 TS 脚本（非纯 SQL）+ 固定 id 配合 `ON CONFLICT (id) DO UPDATE`，数据本体放 `data/education/seed/seed-data.json` | 密码需要运行时哈希计算，SQL 做不到；用固定 id 做幂等键而非 TRUNCATE 重建，避免每次跑测试清空库里其它手工数据 |
| 时间字段用相对"现在"的 `daysOffset` 而非写死时间戳 | 历史/当前/预告三种班期状态的时间关系（过去/最近/未来）不会随日期推移过期失真 |
| 密码哈希用 Node 内置 `scrypt`（`education-api/src/auth/password.ts`），未引入 bcrypt/argon2 依赖 | dev-only 数据，免依赖；格式 `scrypt:salt:hash` 自包含，T-08 登录校验直接复用同一模块，生产前需重新评估 cost 参数 |
| 所有合成账号共用一个明文开发密码 `edu-dev-pass-001`（写在 README，不是每人随机密码） | 开发/教学场景要能登录测试；生产环境不会有共享密码，已在 README 注明 |

### T-08 设计决定（登录/session 部分，资源授权与内部服务认证待学员手写）
| 决定 | 理由 |
|---|---|
| session token 用 sha256 哈希落库，密码用 scrypt | token 本身是 32 字节随机数，猜不出来，不需要故意拖慢；密码是人选的、熵不够，需要慢哈希抗暴力破解。两种哈希解决的是不同威胁，混用同一算法要么密码不够慢、要么 token 校验不必要地慢 |
| 用户不存在与密码错误返回同一个 401/同一条消息 | 分开返回等于让攻击者能批量探测哪些登录名已注册（用户名枚举） |
| session cookie：HttpOnly + SameSite=Lax + 生产环境 Secure；写请求额外校验 Origin/Referer（`requireSameOrigin`） | HttpOnly 挡 XSS 偷 token，SameSite=Lax 挡多数跨站请求，但 cookie 仍会被浏览器自动带上——真正挡 CSRF 的是校验请求发起站点；GET/HEAD 不改状态不查 |
| `withActor` 中间件只解析身份、不做 401；`requireAuth`/`requireRole` 单独挂在需要的路由前 | 同一套身份解析要同时服务"允许匿名"（登录、公开招生信息）和"必须登录"的路由，401 的判断权应该留给具体路由，不能在全局中间件里一刀切 |
| 端口 8400，前缀 `/api/v1`（沿用契约 `servers`） | 8200/8300 已被 legacy/agent 占用；前缀与 openapi.yaml 保持一致，不是另起一套 |
| 资源级授权（某条记录是否属于当前 actor）、BFF→agent 内部身份签发与验签，本轮未实现 | design.md §3 要求的核心机制（不能信任浏览器提交的 actor、内部 token 不进模型提示词），属于本项目分层约定里"必须亲手写一遍"的部分；且当前没有具体资源路由（T-09 才有），先留一个明确边界比提前臆造接口更诚实 |

### T-12 设计决定
| 决定 | 理由 |
|---|---|
| `POST /applications/drafts` 撞到 `applications_one_open_per_enrollment_type` 唯一约束时，按现有申请的状态分两种处理：还在 draft 就当作重复提交、原样返回同一张（AC-006）；已经过了 draft（submitted 及以后）就 409，不悄悄复用 | 契约的 `ApplicationDraft` 响应要求 `confirmation` 字段必填，而已提交的申请不一定还有活着的确认卡；把"这是同一次草稿提交的重试"和"确实已经有一张申请在流转、这次请求本身就不该成立"分开，比硬凑一个不存在的确认卡诚实 |
| `PATCH .../draft` 的 `expectedRevision` 判断直接写进 `UPDATE ... WHERE id=$1 AND revision=$2`，不是先 `SELECT` 出 revision 再判断相不相等 | 先查后判断中间有时间窗口，两个并发 PATCH 会都读到旧 revision、都以为能改，后提交的会覆盖先提交的（T-06 Q1 的 TOCTOU，这次落在 UPDATE 上）；把判断做进 WHERE，数据库保证只有一个能改成功 |
| 确认卡有效期定为 15 分钟，写在代码注释里而非契约/需求文档 | 没有产品侧给出具体数字，是纯工程判断（给学员看清摘要的时间，又不至于让作废的旧摘要长期可用）；不属于业务事实，不写进对外契约，避免以后被当成承诺 |
| `GET /applications/:id` 对"不存在"和"存在但不是你的、也不是老师"返回同一个 404 | 延续 T-08/T-09 已经定下的模式：不用状态码差异告诉调用方"这个 id 是否存在" |
| 幂等键基础设施（`idempotency.ts`）单独抽出、本轮先写好但只接进 confirm 一个端点 | `Idempotency-Key` 在契约里同时出现在 drafts/confirm/approve/refund-result 四个端点上，是同一套机制；写成通用两函数（声明/回填）而不是在每个 handler 里各写一遍，T-13～15 直接复用，不用重新设计 |
| confirm 里两条 UPDATE（claim confirmations、转 applications 为 submitted）包进显式事务，第二条失败就 ROLLBACK，而不是各自独立提交 | 如果各自独立提交，confirmations 的 claim 成功但 applications 的 UPDATE 因为 revision/status 不符而失败时，确认卡已经被标记用过、但申请状态什么都没变——一张烧掉却没有效果的确认卡，学员卡在原地还看不出原因。ROLLBACK 能把这次事务里所有已完成的写操作一起撤销，不只是最后一条 |
| Idempotency-Key 重放时，只有该 key 之前的尝试留下了 `result_id`（证明真的成功过）才直接回读结果；`result_id` 为空一律当成"没成功过"，重新走一遍正常逻辑 | 如果不做这个区分，一次因为确认卡过期而失败的请求，配合客户端用同一个 key 重试，会被误判为"之前成功了"，把一次真实失败悄悄伪装成成功——幂等键要防的是"重复执行"，不能反而用来掩盖失败 |

### T-12 后补充：整体切换到 Drizzle ORM（学员要求，非独立任务编号）
学员反馈手写 SQL 不利于阅读维护，要求把已完成的 6 个路由文件（auth/catalog/cohorts/me/teacher/applications）全部换成 Drizzle query builder。范围只到应用代码；数据库结构的权威来源仍是 `src/db/migrations/*.sql` 手写迁移，`src/db/schema.ts` 只是给 Drizzle 提供类型和列名映射，两边字段必须保持一致但改表结构永远从改 `.sql` 开始。

| 决定 | 理由 |
|---|---|
| Drizzle 只接入查询层，不接入迁移；`migrate.ts` 自定义迁移跑手写 `.sql` 保持不变 | 迁移系统本身在 T-06 已经过测试验证（幂等重跑、篡改检测），迁移换成 drizzle-kit 是另一个更大的决定，不在这次"SQL 好不好读"的诉求范围内；两套迁移方式混用会分裂成两个真相来源 |
| `createApp(pool, opts)` 对外签名不变，内部才用 `createDb(pool)` 包成 drizzle 实例传给各路由 | 测试文件里大量 `pool.query(...)` 直接查库做断言（验证应用层之外的"地面真相"），如果对外也强制换成 db，等于要求测试断言也绕着 ORM 转一圈，反而降低了断言的独立性；只转内部查询逻辑，测试断言继续用原始 `pg.Pool` |
| bigint 字段（`price_cents`/`paid_cents`/`refunded_cents`）在 schema 里声明 `mode:'number'` | 之前每个路由手动 `Number()` 转换（T-09 踩过的坑：pg 驱动把 bigint 序列化成字符串），现在这个转换在 schema 声明一次，所有查询自动拿到 number，不用每个 handler 各自记得转 |
| Postgres 错误码判断（`isUniqueViolation`）抽成 `src/db/pgError.ts` 共享 helper，改为同时看 `err.code` 和 `err.cause.code` | drizzle 把底层 pg 驱动的错误包进 `DrizzleQueryError`，原始 `.code` 挂在 `.cause` 上不再是错误对象的直接属性；两个路由文件（teacher.ts、applications.ts）之前各自维护一份判断逻辑，抽出来避免以后只改一处、漏改另一处 |
| confirm 端点的事务从手写 `BEGIN`/`COMMIT`/`ROLLBACK` 改成 `db.transaction(async tx => {...})`，用抛自定义错误类（`StaleConfirmation`）代替手动判断后调 `ROLLBACK` | drizzle 的事务包装器在回调抛错时自动回滚，不用每个失败分支都记得手动调用 `ROLLBACK`——手写版本能做对，但每加一个失败分支就多一处"记得回滚"的心智负担，用异常代替显式调用是把这个责任交给语言机制而不是靠人记住 |

验证：`npx tsc -b --noEmit` 全工作区通过；`npm test --workspace=education-api` 67 passed（含原有全部反向验证用例）。反向验证：临时去掉 `PATCH .../draft` 里的 `eq(applications.studentId, actor.id)` 过滤，"不是本人的申请：404" 用例按预期变红，恢复后全绿——证明转换后授权判断的语义没有跟着变松。真实开发服务器（drizzle 版）+ 种子账号验证过登录、`/me/enrollments`、`/catalog/current`、创建并确认一张新申请（`db.transaction` 事务路径）、老师批量导入的部分拒绝逻辑；`Promise.all` 真并发确认测试连续跑 5 次稳定通过，确认切到 `db.transaction` 没有削弱原来的并发保护。测试产生的 `submitted` 申请因为 `application_events` 追加式表限制无法清理，与 T-12 时已知的情况相同。

| 学员/老师两个页面各自维护自己的组件树，只共享 `types.ts`/`api.ts`/`applicationLabels.ts` 三个纯数据/纯函数模块，不抽一个通用的"申请详情组件"给两边复用 | 两边看起来像但实际不一样：学员端的操作是"确认/补充/接受拒绝/撤回"，老师端是"要求补充/提方案/批准/拒绝/登记退款"，权限、字段、按钮逻辑都不同。抽一个"通用详情组件"得靠一堆 `role==='teacher'?...:...` 的条件分支撑起来，反而比两个独立组件更难读——这是分类学式分解的反面教材，跟 CLAUDE.md 里"警惕拆成一堆各自都要理解的小碎片"是一个道理 |

### T-15 设计决定
| 决定 | 理由 |
|---|---|
| 金额上限校验放在 `refund-result` 执行登记这一步，不是 T-13 的 `propose` 那一步 | `propose` 只校验 `refundCents >= 0`（T-13 已实现），不查订单余额；真正花钱、需要动 `orders.refunded_cents` 的时刻是登记结果，那才是执行边界该守住的地方——`propose` 时查一遍、执行时再查一遍是重复劳动，且两次查询之间理论上状态可能已经变化，不如只在真正要写钱的那一刻做权威判断 |
| 余额判断直接写进 `UPDATE orders ... WHERE refunded_cents + refundCents <= paid_cents`，不是先 SELECT 算好余额、判断完再 UPDATE | 同一套贯穿全项目的原子性原则（T-06 Q1 起就在用）：先查后判断中间有时间窗口；写进 WHERE，数据库保证这条 UPDATE 本身要么满足边界要么不生效，不依赖应用层的两次往返之间没人插一脚 |
| `applications` 表那条原子 UPDATE 的 WHERE 带 `executionStatus='pending'`，作为"防止重复登记"的第一道判断；`orders.CHECK(refunded_cents<=paid_cents)` 作为数据库层最后一道防线 | 三层防护对应三种失效模式：`executionStatus` 的原子判断防"同一张申请被登记两次"（正常并发/重复调用）；`Idempotency-Key` 防"同一次网络请求的客户端重试"；数据库 `CHECK` 防"前两层都因为未知 bug失效时，金额还是不会被写出负余额或超额"——三层各自堵一种场景，不是互相冗余 |
| Idempotency-Key 的重放判断必须排在"申请当前状态是否允许登记"这个前置校验之前 | 这是本轮测试跑出来的真实 bug：如果先判断"还是不是 pending"，同一个 key 的合法重试在第一次成功之后会因为状态已经变了而被误判成不允许操作，而不是被识别成一次合法重放。confirm/approve 当初写的时候顺序是对的（先判重放），refund-result 是新写的端点，顺序颠倒了，靠这次自己加的测试用例抓出来 |
| 退款 `outcome='completed'` 分支里，除了改 `orders.refunded_cents`，同一个事务内还要把 `enrollments.status` 改成 `ended` | 用户 review 发现的真实遗漏：`enrollments.status` 不是展示字段，`teacher.ts` 里"能不能给某学员标记学习进度"的权限判断直接查它（`status='active'`）。如果退款到账之后不收回，学员报名记录还是 `active`，权限上跟没退费一样，还能继续被记录进度。放进同一个事务而不是登记成功后单独一条语句，是为了避免"钱退了但权限没收回"这种半成功态；`outcome='failed'` 不动 `enrollments`，因为退款没成功，学员本来就该继续保留权限 |

### T-14 设计决定
| 决定 | 理由 |
|---|---|
| **outbox 推迟不做**：T-14 任务描述里写了"outbox"，但 T-06 已经明确把 `outbox_events` 表留到 M3/M4/M5——先跟学员确认过（AskUserQuestion），选择不提前建表。审计靠已有的 `application_events`（每一步状态变化）+ `enrollment_changes`（转班这一类变更的专门历史表）覆盖，不建一个当前没有任何消费方的空表 | 没有 agent/通知消费方之前，outbox 表只是摆设；建了也是"提前设计"，之前 T-06 已经踩过这个判断，T-14 延续同一个决定，不因为任务描述提了一句就推翻 |
| `POST /teacher/applications/:id/approve` 一个端点同时处理 transfer 和 refund 两种类型（分支逻辑），不是拆成两个端点 | 契约里本来就是同一个端点（`teacher/applications/{id}/approve`），拆开会导致契约和实现对不上；转班在事务内直接执行完（executionStatus=completed），退费只是"同意"（executionStatus=pending，真正执行是 T-15 的 refund-result）——两条分支复杂度都不高，不需要为了"看起来单一职责"硬拆成两个路由 |
| approve 的原子 UPDATE 一次性在 WHERE 里判断三件事：revision、confirmed_revision、status 都要对得上 | 这是 AC-008 的核心：revision 防"两个老师并发批准，只有一个赢"；confirmed_revision 防"内容在学员最近一次确认之后又被别的动作改过，老师批的可能不是学员真正同意的版本"（T-13 定下的水位线机制在这里第一次被真正用到）；status 防"申请已经不是 submitted 了还被批准"。三者都写进同一条 UPDATE 的 WHERE，一次原子判断，不是分成三次先查后比对 |
| 转班目标解析用 `proposal?.targetCohortId ?? existing.targetCohortId`；两者都没有就 409，不是允许"老师随便挑一个" | 沿用 T-13 定下的兜底链：目标要么学员建草稿时就知道，要么老师 propose 之后学员 accept 过；approve 端点本身不接收 targetCohortId 参数（契约里没有），如果两边都没有目标，说明流程没走完，不该由 approve 这一步临时决定转去哪 |
| `oldReplayAccess=keep` 时插入的 `replay_entitlements` 行没有设置 `revokedAt`（保持 NULL，即长期有效） | 这是"保留旧班期回放权益"的字面意思——插入即生效，没有到期时间；`revoke` 时干脆不插入这条记录，效果上就是"没有权益"，不需要插入一条又标记撤销的记录再撤销一次，多此一举 |
| 新增迁移 `0006_enrollment_changes_append_only.sql`，给 `enrollment_changes` 补上和 `application_events` 一样的 `forbid_change()` 追加式触发器（之前只是代码约定，没有数据库硬约束） | 学员追问"数据库设计什么时候该改源数据、什么时候该配日志、什么时候该插新行"时发现的不一致：`enrollment_changes` 记录的是和 `application_events` 同一类"不可逆业务事实"，之前却没有数据库层面的强制，只是"代码里从来不写 UPDATE/DELETE"这种约定；补上同一个触发器成本很低（复用已有函数），把两张性质相同的审计表统一到同一个保护级别，不再有一个硬一个软的不一致。真实开发库执行迁移后验证：对已有的一条 `enrollment_changes` 记录尝试 `UPDATE`，报 `enrollment_changes 是追加式表，不允许 UPDATE`；`npm run migrate` 再次执行显示"没有待执行的迁移"（幂等）；`npm test --workspace=education-api` 86 passed |

### T-13 设计决定
| 决定 | 理由 |
|---|---|
| revision 分两类：不经过确认卡的状态变更（supplement/withdraw/request-info/propose/proposal-response 的拒绝分支/reject）一律 `revision+1`；消费确认卡的动作（confirm、proposal-response 的接受分支）不改 revision，只把 `confirmed_revision` 对齐到当前 revision | design.md"锁申请/报名 → 校验 revision 与 confirmedRevision"这句话要求两者能表达"内容有没有在确认之后又变过"；如果消费确认卡的动作也顺手 bump revision，`confirmed_revision` 会立刻等于新 revision，永远追不上，这个校验就失去意义了 |
| `confirm` 与 `proposal-response` 共用同一个事务 helper `claimConfirmationAndTransition`（claim 确认卡 + 转申请状态 + 写审计事件，一次都不行就整体回滚） | 两者是同一个模式（消费确认卡 → 转态），T-12 时已经写过一遍手写事务，T-13 只是换了状态和字段，把公共部分抽出来而不是复制一份几乎一样的事务代码 |
| `proposal-response` 不做 confirm 那种"同一张卡重复调用当幂等重放"的豁免，也不接 Idempotency-Key | 契约里 `proposal-response` 本来就没有 `Idempotency-Key` 参数；重复调用直接落到"确认卡已用" 409，调用方（前端）行为应该是先重新 GET 最新状态，不是静默重试——没有具体 AC 要求这里也做重放豁免，不为了对称而对称 |
| `propose` 签发的新确认卡，`user_id` 记的是学员（`application.studentId`），不是发起请求的老师 | `confirmations.user_id` 只是审计字段（真正的权限判断在 applications 行的 `student_id`），但语义上这张卡是签给"要做决定的人"，老师只是触发了签发动作，混淆了以后审计时会让人误以为是老师自己在确认自己提的方案 |
| `summaryOf` 的 `targetCohortId` 优先取 `proposal.targetCohortId`，草稿原始的 `target_cohort_id` 只在没有方案时兜底 | propose 之后学员看到的确认卡摘要必须是"老师这次提议的目标"，不是学员当初创建草稿时的旧值（大多数场景下就是 null，因为 AC-007 本来就允许创建时不知道目标）——两个字段各显示各的会让确认卡文不对题 |
| `POST /teacher/applications/:id/reject`（终态拒绝整张申请）划进 T-13，不留到 T-14/15 | reject 没有执行副作用（不涉及转班事务或退款登记），跟 supplement/withdraw 这类"纯状态转换"是同一类复杂度；T-14/15 留给真正需要事务+权益变更的 approve/refund-result，任务边界按"要不要执行动作"分更清楚，不是按契约里端点出现的先后顺序生搬硬套 |
| `drafts` 创建、`PATCH draft`、`propose` 三处"写完申请再单独调用 issueConfirmation/revokeActiveConfirmation"补包进同一个事务 | 学员追问"是不是所有多步相关写操作都要加事务"时发现的真实缺口：签发确认卡那条 INSERT 若单独失败，会留下一个没有任何确认卡的申请——`drafts` 还能靠后续 PATCH 补救，`propose` 完全没有补救路径，学员会卡死在 `awaiting_student_confirmation`。反向验证：临时在 `drafts` 事务里于 insert 之后、issueConfirmation 之前抛错，确认 `applications` 表行数没有变化（整个事务回滚），恢复后测试全绿 |

### resume 协议演进讨论（未实现，仅设计笔记）
- 现状：`ResumeBody{type:str, value:str}`，服务端 409 比对 type 与当前 pendingInterrupt。
- 方向：以 `type` 为判别字段的联合类型，每种中断独立 value 结构，格式错配 422、状态错配 409 两层校验；`need_confirm` 的 value 收窄为 confirm/cancel。
- 演进：需要带 confirmationId 时，新增类型名（如 need_confirm_v2）而不是改旧 value 或加可选旁路字段；客户端仅为自有前端/Agent 时可同步升级，无需版本体系。
- type 取值用枚举集中定义；真正唯一来源应是 openapi.yaml（oneOf+discriminator），T-06 后引入类型生成再收敛。

**第 3 步补充决定与发现**

| 决定/发现 | 理由 |
|---|---|
| 确认拆成两个节点：`await_confirmation`（只 interrupt）和 `verify_outcome`（恢复后读事实） | T-04 已验证恢复时被中断的节点从头重跑；interrupt 之前不做副作用，恢复后的读取放在下一个节点，各自幂等 |
| 恢复信号（`Command(resume=...)`）内容被丢弃，决定只看业务 API 的最新事实 | design.md："不把'确认'文本当成授权"。真正的确认是学员在界面上对业务 API 的 POST；测试里信号声称"已确认"而业务库仍是草稿，图回答"还没有看到你的确认" |
| 恢复后的话术是代码生成，不调模型 | 状态和金额类表述不应由模型即兴发挥；也让恢复路径无需模型可用 |
| 挂起时学员发新消息 → LangGraph 把它当作新的一轮从 START 运行，旧挂起被丢弃（实测） | 不会卡死；草稿仍留在业务库，可随时在界面确认 |
| 没有在图内做"线程归属"检查 | 图的输入在节点运行前就写入 checkpoint，图内挡不住"往别人线程里发消息"；跨 actor 的恢复由业务 API 兜住（实测 404） |
| 原测试里"actorId 不在 checkpoint"的断言改为只断言 token | actorId 不是凭证；真正要保证不落库的是 token（现在两者在真实 Postgres 上都查了，结果均为不在） |
| **踩坑**：清理联调数据时 `application_events` 拒绝 DELETE（追加式审计表，触发器保护） | 这是有意的完整性设计，不绕过触发器；改为经业务 API 撤回该申请（追加一条事件），联调遗留 1 条 withdrawn 记录作为历史。教训：联调若要走到"提交"，会留下不可删的审计行，改用一次性数据库或接受遗留 |

**遗留给 T-20 的三条约定**：①恢复信号只是叫醒图，内容不参与决定；②线程 id 必须由已校验的 actor 派生（如 `{actorId}:{会话id}`），否则图内无法阻止别人往我的线程写入；③一次运行的工作证 60 秒有效，等待确认之后的恢复必须由 BFF 用新请求重新签发并传入新的 `RunScope`（在接口入口构造，因 `context_schema` 不校验类型）。

**更正记录**：曾凭函数签名推测"ToolNode 默认把异常文本回填给模型"，实测不成立（见上，普通异常直接抛出）。结论以实测为准。
**注意**：`langchain-openai` 默认注入自定义 transport，会关闭 httpx 对系统代理的自动识别；开发环境走代理时需传入自己的 `http_async_client`。


### T-20 设计决定

| 决定 | 理由 |
|---|---|
| 流式从一开始就是逐 token（用户拍板） | 前端体验；同时倒逼模型接口在 T-20 就支持流式，不留到接真实模型时再改 |
| 流式经"回调 + LangGraph 自定义流通道"送出，不依赖 LangGraph 的 `messages` 流模式 | 我们的模型层是自有接口（消息是普通字典），LangGraph 的 `messages` 模式靠 LangChain 回调捕获，接不到自有接口；自定义通道对事件内容有完全控制（脱敏） |
| 事件只是通知，不影响任何行为；最终回答以 `message.completed` 里的完整文本为准 | design.md 要求 completed 带完整文本供客户端核对；固定话术（确认卡等）不是模型生成的，不会有 delta；ReAct 中"调用工具前的话"也会流出，客户端以 completed 为准 |
| 并发锁用"runs 表部分唯一索引"：同一会话至多一条 status='running' | 沿用 M2 的教训：不变量由数据库唯一约束保证，不靠应用层先查后写；冲突返回 409 RUN_IN_PROGRESS |
| 租约 90 秒（用户拍板）：BFF 在收到事件时续租（节流），新消息到来时先把 lease 已过期的 running run 标记为 failed 再抢占 | 单个 run 的预算+超时最坏情况远低于 90 秒；不做续租则 BFF/Agent 崩溃后会话永久 409 |

### T-25 设计决定：分片边界稳定性（2026-10-01 讨论，接受现状不改代码）

`chunk.ts` 按累加字数/时间间隔贪心合并，边界依赖"从上一个边界到现在攒了多少"——这是个全局累加量，文档中间任意一处内容变化，都可能让后面所有分片的分组方式跟着偏移，级联废掉 `content_hash`（T-26 判断"要不要重新生成向量"的依据）。讨论过程：

1. **确认问题真实存在，不是理论假设**：用学员提供的真实 VTT 文件实测，184 条 cue 里间隔超过 2 秒的次数是 0——ASR 转录出来的 cue 时间戳是连续的，"自然停顿"这条分段规则在真实数据上从未触发，84 个 segment 全部是纯粹按 320 字累加切出来的，级联风险是真实存在的，不是边缘情况。
2. **调研 content-defined chunking（CDC，类似 rsync/restic/FastCDC 的滚动哈希分片）**：这是业界对"局部编辑不传染全局"这类问题的标准解法（边界只取决于局部滑动窗口内容，不取决于累加量）。调研 npm 生态（`fastcdc`、`@dstanesc/wasm-chunking-fastcdc-node`、`rabin-wasm`、`gearhash-jit`）后发现：全部面向二进制设计（`Buffer`/`Uint8Array`，按字节滚动窗口），中文 UTF-8 变长编码下切断多字节字符中间的风险没有任何库处理；且这些包普遍维护质量差（个人维护、多年未更新、或需要 Rust/WASM 原生编译的部署负担）。结论：不引入第三方包，真要做 CDC 得自己写，但没必要——见下一条。
3. **重新界定问题范围，发现不需要 CDC 这么重的方案**：SRT/VTT 来自录播转录，录完不会再改（顶多整份重新转录），级联风险对它们不成立，只有 Markdown 讲义会被老师编辑。讨论过"一段一个 segment、不合并"（彻底消除级联，代价是短段落检索上下文更碎）和"段落自身长度不够才合并"（论证后发现仍是累加逻辑的变体，短段落连续出现时同样会级联，不能解决问题）两个方案。
4. **最终决定：保持现状，接受级联风险，不改代码**。理由：小改动（改几个字）影响范围有限，大改动（增删整段）本来就值得整份当作新内容重新生成——`version` 机制本来就是为"整份当新版本处理"设计的，级联到整份重新生成向量和"干脆当一份新文档对待"在效果上没有本质差别。真正能完全避免级联的方案（一段一个 segment）要用"检索时上下文更碎"换"编辑更稳定"，这笔交易现在不划算。T-26 做索引优化时如果发现重新生成向量的成本确实是实际瓶颈，再回头考虑是否要牺牲一些分片质量换稳定性。

### 已知局限

- 对话历史无界累积，缺一整套生产级上下文/存储治理（2026-09-30 讨论发现，逐层展开）：`GraphState.messages` 的 reducer 是 `operator.add`（student_graph.py:88），每轮只追加不裁剪；`load_authorized_context` 重置的只是 `branch`/`stop_reason`/`reply`/`confirmation`，不包含 `messages`（student_graph.py:107-112）。服务端每次只传入新的一条用户消息（server.py:72），靠 checkpoint + reducer 把历史累积起来，`route`/`branch_node` 每轮都会把**全部**历史重新发给模型（student_graph.py:116、125）。这不是单一问题，至少有六层，逐层记录：
  1. **（已解决，2026-09-30）模型输入长度**：token 开销随对话轮数近似平方级增长，长历史里的噪声还会干扰路由分类和工具循环的判断质量。**实现**：`student_graph.py` 新增 `HISTORY_TOKEN_BUDGET`（近似 token 预算）+ `_trim_to_budget`，在 `route`/`branch_node` 组装模型输入前调用，直接复用 `langchain_core.messages`（`convert_to_messages`+`trim_messages(strategy="last", token_counter="approximate", start_on="human")`）——没有自造裁剪算法：`start_on="human"` 是库自带的保证，裁剪结果要么以一次完整用户发问开头，要么整段丢弃，绝不会把某一轮的工具调用和它的结果拆散；裁剪只作用于"这次发给模型看的"临时列表，最终仍返回原始字典切片，不改变 `Message` 的持久化格式，也不碰 `state["messages"]`/checkpoint（**不需要改 reducer**）。`langchain-core` 原本是 `langgraph`/`langchain-openai` 的传递依赖，现已在 `pyproject.toml`/`uv.lock` 显式声明。测试：`tests/test_student_graph.py` 新增 `test_old_turns_are_trimmed_once_history_exceeds_the_token_budget`（裁剪只影响模型输入、checkpoint 里的持久化历史保持完整）与 `test_trimming_never_splits_a_tool_call_from_its_result`；`uv run pytest` 135 passed、4 skipped（含真实 Postgres 的重启恢复用例）。
  2. **（已解决，2026-09-30）checkpoint 行数**：LangGraph 默认每一步图执行都存一条 checkpoint（为支持时间旅行/调试回放），行数随"图跑了多少步"增长，与消息数无关，裁剪消息解决不了这一层。**踩坑记录**：`BaseCheckpointSaver.aprune(thread_ids, strategy="keep_latest")` 文档上正是为这个场景设计的，一度接入 `server.py` 的 `_stream_run`，但实测 `InMemorySaver` 和真实 `AsyncPostgresSaver`（`langgraph-checkpoint-postgres` 3.1.2，PyPI 当前最新版）都没有真正实现它，直接走到 `BaseCheckpointSaver` 的 `raise NotImplementedError` 默认实现；已撤回。**调研**：[langgraph#8531](https://github.com/langchain-ai/langgraph/issues/8531) 确认这是官方还在跟踪、未合并的已知缺口（此前 PR #6883 因可能破坏 `DeltaChannel` 的可恢复性而未采纳）；[官方 Persistence 文档](https://docs.langchain.com/oss/python/langgraph/persistence) 明确说自托管场景没有内置自动清理，"建议自己加一个 cron job"——手写清理任务是官方认可的路，不是重复造轮子。**关键安全前提**：issue 里反复强调的风险是 `DeltaChannel`（值依赖"从某个快照开始重放增量"，误删旧 checkpoint 会让它悄悄拼出空值而不报错）；直接打印过 `student_graph.py` 编译出的图，所有 channel 都是 `BinaryOperatorAggregate`/`LastValue`/`EphemeralValue`，**没有一个是 `DeltaChannel`**，这条风险在我们这里不成立。**实现**：新增 `checkpoint_cleanup.py` 的 `prune_thread_checkpoints(dsn, thread_id)`，按 issue #8531 给的安全算法——查最新 checkpoint 的 `channel_versions`（这是一份指向 `checkpoint_blobs` 真实值的"目录"，不是完整值本身，同一个 blob 版本会被好几条 checkpoint 共享引用），只删不在这份目录里、不再被引用的 blob，`checkpoints`/`checkpoint_writes` 只保留最新 `checkpoint_id` 对应的行，全程一个事务；`server.py` 的 `create_app` 新增 `checkpoint_dsn` 参数，给了才在每次运行后的 `finally` 里调用（失败只记日志，不影响已完成的响应），测试用的 `InMemorySaver` 留空即可，不反射 `graph.checkpointer` 的类型。`main.py` 用真实 `DATABASE_URL` 接入。反向验证：把"只删不再需要的 blob"改成"无条件删这个线程全部 blob"，`confirmation` 字段的 blob 被误删，恢复时 `KeyError`，对应测试正确变红，已恢复。测试：`tests/test_checkpoint_cleanup.py`（真实 Postgres）验证多轮对话裁剪后行数收口到 1 且状态完整可读、**裁剪一个挂起在 `await_confirmation` 的线程后依然能正确恢复**（最关键的场景）、`server.py` 端到端接入后自动收口、不传 `checkpoint_dsn` 时不碰 Postgres、清理失败被记日志但不影响已成功的响应。`uv run pytest` 141 passed、4 skipped。
  3. **（已解决，2026-09-30）checkpoint 单行体积（复合效应）**：在做持久化裁剪之前，每条 checkpoint 存的是当时的全量状态，包含到那一刻为止的全部 `messages`——"行数"和"单行体积"两个因子都在随对话增长，总存储量是复合增长。**实现**：用 `langgraph.types.Overwrite`（公开 API，明确文档为"绕过 reducer、直接写入 `BinaryOperatorAggregate` channel"）在 `respond`/`verify_outcome`——每一轮 query/application/handoff 分支的共同出口——把持久化的 `state["messages"]` 用同一个 `_trim_to_budget(..., HISTORY_TOKEN_BUDGET)` 真正裁掉，不再只是裁"发给模型看的"临时副本。**关键正确性风险（由第三方 Codex 分析指出，已核实并处理）**：转人工摘要（`handoff.py` 的 `build_handoff_summary`）此前靠扫描完整 `state["messages"]` 提取"已核验事实/相关申请/学员原话"，一旦裁掉较早轮次，这些信息会在没有任何报错的情况下从摘要里消失。**修复**：把 `handoff.py` 拆成 `extract_from_messages`（纯函数，可对增量消息反复调用）+ `build_handoff_summary`（只管拼字符串），`GraphState` 新增 `handoff_quotes`/`handoff_facts`/`handoff_applications`/`handoff_failures` 四个跨轮累加、不随 `messages` 裁剪而丢失的字段（各自配一个 `merge_*` reducer：分别是"保留最近 N 条""去重+封顶""按 id 合并取最新"）；`load_authorized_context`（每轮必经入口）增量捕获这一轮的学员原话，`branch_node` 只对 `run_tool_loop` **新增的**那几条消息（不是全部历史）做增量抽取，避免裁剪后又要重新扫一遍历史。反向验证：分别去掉 `respond` 的 `Overwrite` 调用、去掉 `load_authorized_context` 的引用捕获，对应新测试均正确变红，已恢复。测试：`tests/test_student_graph.py` 新增 `test_handoff_facts_survive_even_after_the_originating_turn_is_trimmed_away`（核心不变量：被裁掉轮次的事实仍留在交接摘要素材里）；原 `test_old_turns_are_trimmed_once_history_exceeds_the_token_budget` 的断言反向改写（此前断言"checkpoint 保留全量"，现在断言"checkpoint 也被裁剪"）；`tests/test_handoff_summary.py` 改用新的 `extract_from_messages`+`build_handoff_summary(quotes=, facts=, applications=, failures=, reason=)` 两段式 API，原有用例不变。`uv run pytest` 136 passed、4 skipped。
  4. **硬限制来临前的可观测性缺失**：目前没有任何地方记录/监控某个 thread 的消息数或 token 数，运维不会提前知道哪个会话快撑爆了，只会在真的超限那一刻从模型 API 收到报错。方案：在 `route`/`branch_node` 或 `_stream_run` 里加一个简单的计数/日志埋点，为后续告警留口子。
  5. **硬限制来临时无优雅降级**：即使做了第 1 层裁剪，阈值算错或极端场景漏网仍可能撞到模型 API 的硬性上限，现在代码没有对"模型返回上下文超限错误"这个分支做兜底——会直接向上抛异常。方案：捕获该类错误，回复类似"这个对话太长了，请开一个新的会话"的可控话术，而不是让请求整体失败。
  6. **（已解决，2026-09-30）数据保留/合规**：这是教育场景，聊天记录可能涉及未成年人或监护人的个人信息，"无限期存储原始对话内容"不只是存储成本问题，也是数据保留策略/合规问题（例如是否需要支持"删除某学员历史对话"）。这和摘要压缩是两件独立的事——压缩解决存储量，合规可能要求原文到期必须真删除而不只是压缩存档。**实现**：`adelete_thread(thread_id)`（真实 `AsyncPostgresSaver` 已实现，非 `NotImplementedError` 兜底；`InMemorySaver` 也同样实现，测试不需要真实 Postgres）能整条删除某个线程的全部 checkpoint（`checkpoints`/`checkpoint_blobs`/`checkpoint_writes` 三张表一次删净，不是部分裁剪，所以不用像第 2 层那样担心哪个 blob 还被引用）。新增 `server.py` 的 `DELETE /internal/threads/{conversationId}`——沿用 `/internal/runs` 同一套信任模型（`X-Actor-Context` 验签、thread id 按 actor 派生，调用方物理上无法删别人的线程），删除幂等（线程不存在也返回 204，不泄露"这个线程存不存在"）。**明确划清的边界**：这个接口只负责"能删"这个能力本身；由谁、在什么时机决定要删（学员自己操作、还是运营处理合规请求），以及 BFF 自己的 `messages` 表要不要一并删除，是 BFF/产品侧尚未做出的决定，这次没有一并设计——目前没有任何调用方触发这个接口，是刻意留白，不是遗漏。反向验证：去掉 `thread_id` 里的 `actor_id` 前缀，"只删自己线程"的隔离测试和基本删除测试都正确变红，已恢复。测试：`tests/test_agent_server.py` 用 `InMemorySaver` 验证鉴权、删除后状态清空、幂等、线程隔离、依赖失败映射到 503；`tests/test_checkpoint_cleanup.py` 加了一条真实 Postgres 用例，确认三张表真的清零而不是只删了目录。`uv run pytest` 146 passed、4 skipped。
  第 2 层的摘要压缩（`langmem.short_term.SummarizationNode` 那条路）仍然是备选加强项，见下面"摘要压缩 vs 纯截断"的讨论，评估后推迟到 M6a。M3 范围内六层里第 1、2、3、6 层已解决；剩余 4、5 挂到 M6b。留给后续里程碑或作为 L-03 独立练习的候选题。

  **调研后否决的方向（2026-09-30，第 3 层解决后讨论出的替代方案）**：曾考虑把"跨轮记住 messages"的责任从 Agent 的 checkpoint 完全转移给 BFF——`/internal/runs` 请求体加一个 `history` 字段，BFF 查自己的 `messages` 表传入，Agent 不再自己维护跨轮 `messages`。查了两篇文章后否决：
  - [Why my LangGraph agent throws away its checkpoint on every request](https://dev.to/akashpersetti/why-my-langgraph-agent-throws-away-its-checkpoint-on-every-request-21ff)：这是 AWS Lambda 冷启动、checkpoint 不可靠场景下的权宜之计，作者自己踩的坑是"跨轮的编排状态（重试计数器、评审反馈）跟着 messages 一起被重置"、"无条件写入导致并发请求互相覆盖"。我们的前提（Lambda 无状态部署）根本不成立——education-agent 是常驻进程 + 真实 Postgres checkpointer，T-04 已验证 kill -9 重启可恢复，没有这篇文章要解决的那个问题。
  - [LangGraph + PostgreSQL: Chat history and summarization best practice](https://forum.langchain.com/t/langgraph-postgresql-chat-history-and-summarization-best-practice/3521)：社区/官方推荐的是两层架构——"checkpoint 只存摘要+最近 N 条，作为 LLM 工作上下文；应用自己的表存完整历史，只追加不删除，给 UI 用"，原话"checkpoint 不是消息存储，而是 LLM 上下文管理工具"。这正是我们已经在用的架构（`education-api` 的 `messages` 表是完整历史，`education-agent` 的 checkpoint 经第 3 层修复后是有界工作上下文），不需要再往"完全搬到 BFF"那个方向走。
  - 且这个重构即使做了也解决不了第 2 层：不管 `messages` 从哪来，LangGraph 每一步图执行照样写一条 checkpoint，行数增长和消息来源无关。
  结论：第 1、3 层已实现的方案就是社区推荐的正确形状，不做这次跨服务重构。

  **摘要压缩 vs 纯截断（2026-09-30）**：社区推荐用 `SummarizationMiddleware`/`langmem.SummarizationNode` 把"直接丢弃"换成"先摘要再丢弃"，避免模型彻底忘记很久以前的内容。评估后决定**推迟到 M6a**（真正接入真实模型之后）：摘要质量没法用当前的 mock 模型（`dev_model.py`，纯关键词规则）验证，现在做了也测不出好坏；而且转人工摘要已经靠独立的 `handoff_quotes/facts` 字段保护，不依赖 `messages` 是否完整，纯截断造成的唯一影响是"模型可能忘记很久以前聊过什么、需要重新问一次"，是优雅降级而非正确性缺陷，教育客服场景的对话长度也大概率不会经常触发这个问题。
